## 3. 实现方式说明

### 3.1 整体思路

软件分成三层：AutoCardCopier.Core（领域逻辑，不引用任何 WPF 类型，可被控制台测试直接调用）、
AutoCardCopier.App（WPF 界面，只做绑定与编排）、AutoCardCopier.Tests（自研控制台测试运行器）。
这样分层的目的很实际：拷卡逻辑（命名、拷贝、校验）是风险最高的部分，必须能脱离界面被反复自动测试。

界面采用自研极简 MVVM（ViewModelBase + RelayCommand + AsyncRelayCommand），不引入任何第三方框架；
所有耗时操作都在后台线程执行，进度通过 IProgress 回到界面线程并按 200 毫秒节流，
因此拷贝几十 GB 素材时界面依然可以正常操作。

数据存储一律使用 JSON 文件（DataContractJsonSerializer + 缩进美化）：
设置、项目库、任务历史、清单、流水日志都是纯文本，出问题时可以直接用记事本看，
不需要数据库，也不需要用户安装任何东西。

### 3.3 关键实现说明

**（1）卡片识别为什么要多重判定**
CFexpress / XQD 读卡器经常被 Windows 报告为“固定磁盘”，如果只看 DriveType.Removable 就会漏识别；
反之如果放宽到“所有固定磁盘”，就有误格式化的风险。因此判定顺序是：
排除系统盘 → 是否含 DCIM/M4ROOT/AVCHD/XDROOT/PRIVATE 等素材目录 → 卷标是否命中相机卡命名 → 可移动介质兜底。
同时用“卷序列号 + 卷标 + 容量”生成卡片指纹，做到换盘符也能认出是同一张卡。

**（2）拷贝为什么不会留下半截文件**
拷贝不是直接写目标文件名，而是先写 `目标名.acctmp`，写入完成后比较长度，确认无误再用 File.Move 改名。
取消或异常时删除临时文件。这样即使拷到一半拔卡或断电，目标目录里也只会多出一个可识别的临时文件，
不会出现“看起来正常但其实是坏的”素材。

**（3）默认校验档位为什么是“大小 + 抽样哈希”**
全量 SHA-256 对 200 GB 素材来说耗时太长（可能接近甚至超过拷贝时间），
而每文件取首 1 MB、中点 1 MB、尾 1 MB 三段做哈希，既能发现绝大多数传输损坏，耗时又可控。
需要绝对严格时可在设置里切到 CRC32 或 SHA-256 全量。

**（4）格式化护栏为什么写成不可配置**
格式化是不可逆操作，一旦误判就是灾难。护栏直接写在 DiskSafetyInspector 里：
系统盘、网络盘、光驱、内置磁盘（接口不是 USB）、没有校验凭证、卡片指纹不一致，任意一条命中即拒绝。
测试里专门覆盖了这些拒绝路径，并且“被拒绝时不得删除或修改任何文件”也有断言。

## 5. 遇到的问题与解决过程

| 问题 | 现象 | 定位过程 | 解决方式 |
|------|------|----------|----------|
| 本机没有 .NET SDK 与 4.x 参考程序集 | dotnet build 不可用，MSBuild 报找不到参考程序集 | 逐个探测 dotnet、MSBuild、参考程序集目录 | 用 MSBuild 18 + FrameworkPathOverride 指向系统运行时目录，并用最小 WPF 探针工程验证通过 |
| 本机 PowerShell / curl 的 HTTPS 不可用 | schannel 报 SEC_E_NO_CREDENTIALS，无法下载工具 | 对比 PowerShell、curl、Python 三条链路 | 改用 Python 的 OpenSSL 下载便携版 MinGit，满足版本控制需求 |
| 生成代码中的反斜杠转义 | PathUtil 中字符字面量变成单反斜杠，编译报“常量中有换行符” | 用 Python 打印文件真实字符码定位 | 改为使用 Path.DirectorySeparatorChar，避免手写反斜杠字面量 |
| 类名与类型名冲突 | FileLogger 的属性名 Directory 覆盖了 System.IO.Directory；TaskJournal 的 Path 同理 | 编译错误提示“string 未包含 CreateDirectory” | 属性改名为 DirectoryPath / FilePath，并在内部显式使用全名 |
| TaskStatus 名字冲突 | 与 System.Threading.Tasks.TaskStatus 歧义 | 编译错误 CS0104 | 用 using 别名显式指向领域枚举 |
| PowerShell 脚本中文与执行策略 | 直接运行 build.ps1 被策略拦截；改为 BOM 前脚本被当成 ANSI 解析，中文报错 | 逐步缩小：先解决执行策略，再解决编码 | 脚本保存为“UTF-8 带 BOM”，并提供 build.cmd / test.cmd 包装（内部使用 -ExecutionPolicy Bypass） |
| cmd 包装脚本中文注释 | cmd.exe 按 ANSI 解析批处理，中文注释被当成命令 | 观察错误信息中出现被截断的中文 | 批处理文件内只使用英文注释 |

## 8. 经验与提醒

- **不要手写反斜杠字面量**：生成 C# 代码时用 Path.DirectorySeparatorChar 之类的 API 代替 '\\'，可以避开一整类转义错误；
- **属性命名避开 BCL 类型名**：Directory、Path、TaskStatus 这些名字很容易和系统类型冲突，建议加后缀；
- **PowerShell 脚本一律保存为 UTF-8 带 BOM**：Windows PowerShell 5.1 对无 BOM 的 UTF-8 会按 ANSI 解析，中文注释会直接让脚本无法执行；
- **GUI 项目也要留自动化测试**：核心逻辑全部放在 Core 里，界面只做绑定，这使得 64 个用例可以在 1 秒内跑完；
- **危险操作的安全护栏要写成“默认拒绝”**：格式化相关代码先判定拒绝路径，再判定允许路径，测试优先覆盖拒绝路径。
