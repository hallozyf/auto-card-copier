# 排故报告 · BUG-002：点击“开始拷贝”后界面卡死（F11 引入）

> **报告编号**：BUG-002 ｜ **严重级别**：严重（主流程不可用）｜ **状态**：已回滚代码，重写方案待评审
> **发现方式**：用户实机反馈 ｜ **报告日期**：2026-10-12 ｜ **影响版本**：v0.2.0（F11 多目标备份）
> **已执行处置**：src 回滚到 v0.1.1（文档保留），构建与 72 个用例通过

---

## 1. 现象

用户反馈“点击拷贝的一瞬间发生崩溃”。经查证：**不是崩溃，而是界面线程被阻塞导致的挂起（无响应）**，
Windows 错误报告将它记录为 AppHang（应用程序挂起），而不是 AppCrash。

## 2. 证据链

### 2.1 程序日志时间线（用户数据目录 logs\app-2026-10-12.log）

```
22:50:30.520 [DEBUG] 设置已校验并归一化                    ← 用户在设置页保存（副目标 = Z:\照片）
22:50:36.902 [INFO]  拷贝计划已生成：402 个文件，8.1 GB，目标目录 H:\2026\...
                    （此后没有任何日志：没有目标完成、没有拷贝结束、也没有程序退出）
22:51:08           Windows 错误报告：AppHangB1  AutoCardCopier.App.exe
22:51:31           [INFO] 程序启动（用户强杀后重新打开）
...
22:58:03           [INFO] 扫描完成：506 个文件，13.1 GB
22:59:43           Windows 错误报告：AppHangB1  再次挂起
```

### 2.2 数据目录留下的痕迹

| 检查项 | 结果 | 推论 |
|--------|------|------|
| history.json 中该任务是否有“进行中”记录 | **没有** | 流程从未执行到任务记录写入 |
| 数据目录 tasks 下是否有计划文件 | **没有**（目录都不存在） | 流程从未执行到续传计划写入 |
| 是否有 .NET Runtime 异常事件 | **没有** | 排除“未处理异常导致崩溃” |
| 是否有异常日志（界面线程未处理异常） | **没有** | 同上 |
| WER 事件类型 | AppHangB1（挂起） | 界面线程长时间无响应 |

结论：任务卡在“计划已生成”与“写入任务记录”之间，属于**阻塞**而非异常。

### 2.3 对照实验

| 时间 | 配置 | 结果 |
|------|------|------|
| 21:53 | 只有主目标 H:（未配置副目标） | 成功拷贝 346 个文件并校验通过 |
| 22:50 | 22:50:30 刚把副目标设为 Z:\照片 | 点击拷贝即挂起 |

两次唯一的差异：**新增了网络位置的副目标**。

---

## 3. 根因分析

### 3.1 直接原因：F11 把网络 I/O 放到了界面线程上

v0.2.0 的拷贝流程改成：

```
StartCopyAsync（在界面线程上同步执行，直到第一个 await 之前）
  └─ Backup.BuildPlans(...)                     ← 仍在界面线程
        └─ 对每个目标：CopyPlanBuilder.Build(...) ← 内部全部是同步 I/O
              ├─ ResolveConflict → Directory.Exists(目标项目目录)
              └─ 逐文件 ShouldSkipExisting → File.Exists(目标文件)   ← 402 次
```

- 主目标 H: 是本地盘，402 次文件存在性检查很快；
- 副目标 Z:\照片 在 NAS 上，**每一次 File.Exists 都是一次同步 SMB 往返**，402 个文件即数百次往返；
  若目标一时不可达，单次调用还会按 SMB 超时等待；
- 这些调用全部发生在**界面线程**上，于是窗口“未响应”，Windows 记录为 AppHang。

### 3.2 为什么旧版本没有这个问题

v0.1.1 只有一个目标（主目标，本地盘），计划生成阶段同样有逐文件探测，但本地盘耗时可忽略。
F11 把目标数量变成 2 个，却没有把新增目标带来的网络 I/O 移出界面线程，也没有任何超时保护。

### 3.3 流程层面的失误（比代码缺陷更值得记录）

技术文档 docs/02 第 2.4 节早已写明硬性原则：“**UI 线程不执行耗时 I/O，所有耗时操作在后台线程**”。
F11 的实现违反了这条自己定下的原则；而我既没有在动手前把它落实为设计约束，也没有在自测中覆盖
“网络目标 + 大量文件”的场景。这正是跳过评审流程的代价：如果先写技术文档，这一条必须写进
“实现路径”与“测试用例”，评审时就会暴露。

## 6. 重写方案（待评审，批准后才动代码）

| 编号 | 修复点 | 具体做法 |
|------|--------|----------|
| R1 | 目标探测与计划生成移出界面线程 | 计划生成与预检全部通过后台任务执行；界面线程只更新状态文本 |
| R2 | 目标可达性检查带超时 | 用带取消的后台任务检查“目录存在 + 可写 + 剩余空间”，超时（建议 3 秒）即判定不可用并给出明确提示，绝不阻塞 |
| R3 | 取消逐文件的同步探测 | 网络目标不再在计划阶段做文件存在性检查；改为拷贝阶段在后台线程按需判断，或对网络目标直接执行“写临时文件 + 大小比对 + 原子改名” |
| R4 | 失败即返回 | 目标不可用时立即返回该目标结果（副目标失败不影响主目标），界面显示原因 |
| R5 | 界面反馈 | 多目标时显示“正在检查目标可用性…”并可取消；进度区分目标序号 |
| R6 | 回归用例 | 新增：不可达副目标不阻塞且主目标成功；400 个文件的计划生成在后台完成；用超时断言保护界面线程无同步 I/O |

**流程要求**：先更新 docs/10（需求：增加“目标可用性检查与超时”“不得阻塞界面”的验收标准）
与 docs/11（技术：增加异步化设计、超时参数、风险与回归测试），**提交你评审批准后再开始改代码**。
