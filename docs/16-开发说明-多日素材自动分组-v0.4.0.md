## 2. 关键实现

1. **时间提取只读文件头**：照片 64 KB、视频头尾各 256 KB（部分录像机把 moov 写在文件末尾）；
2. **异常时间不采信**：早于 1990 年或晚于当前时间 +1 天一律回退，宁可标"未知日期"；
3. **分组是 O(n) 单遍分桶**，未知时间不混入任何日期；
4. **执行单元 = 项目 × 目标**：每个单元有独立的计划、拷贝结果、校验报告；
5. **并行与限流**：项目级并行度由设置控制，所有单元共享一个文件级信号量（CopyEngine 新增 sharedGate 参数），避免"项目并行 × 文件并行"导致并发暴涨；
6. **执行前复检目标可用性**：从生成计划到开始执行之间可能拔盘/断网，此时把该目标的单元直接标记失败，不再浪费时间；
7. **进度聚合**：各单元上报的进度按增量累加成整体进度，界面显示项目序号（第 N/M 个项目）。

## 4. 遗留问题

| 编号 | 问题 | 说明 |
|------|------|------|
| R1 | 需用户真机验证 | 用跨多天的真实卡验证分组日期与项目名；特别关注视频日期是否正确（若某相机容器时间不准，打开"视频按文件时间"） |
| R2 | 手动合并/拆分分组 | 按批准范围放二期 |
| R3 | 界面为 ItemsControl 全量渲染 | 分组数很多（>50）时建议改为虚拟化列表；当前按需求预期（几天到几十天）足够 |
| R4 | 拍摄时间提取耗时 | 400 文件量级实测在秒级；超大卡可切快速模式 |

## 5. 经验

1. 时间来源必须"可解释"：把来源展示出来，用户才能判断某个日期是否可信；
2. 并行要成对出现：项目并行必须配一个全局的文件级闸门，否则并发会失控；
3. 计划与执行之间要复检外部状态（目标可用性），否则用户拔盘后会看到一堆莫名的失败。
