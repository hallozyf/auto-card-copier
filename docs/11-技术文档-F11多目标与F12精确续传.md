## 1. 涉及技术

| 领域 | 技术 |
|------|------|
| 多目标协调 | 异步串行编排；每个目标拥有独立的拷贝计划与校验报告 |
| 进度模型 | 用包装器给进度对象注入目标序号与标签，界面无需感知多目标细节 |
| 精确续传 | DataContractJsonSerializer 持久化任务计划；逐文件状态机（Pending / Done / Failed） |
| 原子写入 | 临时文件加重命名的原子写入；长路径统一走 PathUtil 包装 |
| 时间处理 | 高精度 ISO 格式（7 位小数）与 UTC 专用解析，保证续传后时间戳不失真 |
| 测试 | 自研控制台运行器，新增 11 条用例（F11 六条、F12 五条） |

## 2. 实现路径

### 2.1 F11 多目标备份

处理流程（三段式）：

1. 目标解析：主目标必须存在，否则拒绝整个任务；副目标为空则忽略，与主目标相同则拒绝，不存在则记录警告并跳过；
2. 计划生成：对每个目标分别调用计划生成器，各自处理目录冲突，项目相对路径保持一致；
3. 串行执行：对每个目标依次执行“预检 → 拷贝 → 校验”，任一环节失败只影响该目标，最后汇总为全部成功 / 部分成功 / 全部失败。

进度对象中新增目标序号与目标标签两个字段，由协调器在转发进度时填充，界面据此显示“第几块盘”。

### 2.2 F12 精确断点续传

1. 任务开始：生成任务号与项目号，写出计划文件，所有文件初始状态为待处理（若计划项本身是跳过，则直接记为已完成）；
2. 执行期间：拷贝引擎每成功一个文件就把目标路径追加到结果的完成列表；
3. 每轮结束（含取消与校验之后）：把完成与失败状态回写计划文件并保存；
4. 正常完成：校验与覆盖率检查通过后删除计划文件；
5. 异常中断：计划文件保留；下次启动时任务历史会发现状态仍为“进行中”的记录，据此加载计划文件并提示剩余数量；
6. 继续任务：把计划文件中已完成的项目标记为跳过，还原为可执行的拷贝计划，交给协调器执行；完成后重新校验与覆盖率检查，通过则删除计划文件并解锁格式化。

## 3. 数据结构（任务计划文件）

| 字段 | 说明 |
|------|------|
| schemaVersion、taskId、projectId | 版本、任务号、项目号 |
| projectName、shootDate、location、shootType、photographer、cameraModel | 还原项目上下文所需信息 |
| cardFingerprint、cardLabel | 卡片指纹与卷标，用于识别是不是同一张卡 |
| sourceRoot | 卡片根目录，续传时用于判断源卡是否已连接 |
| targets 数组 | 每个目标：根目录、是否主目标、项目目录、项目相对路径、项目名 |
| items 数组 | 每个文件：源路径、目标路径、字节数、最后写入时间（高精度 ISO）、类型、状态、错误信息 |
| createdAt、updatedAt | 创建与更新时间 |

## 4. 关键实现细节与设计取舍

| 决策 | 原因 |
|------|------|
| 多目标串行执行 | 两个目标常共享物理链路，并行会互相抢磁头与带宽，整体更慢；串行结果也更可预测 |
| 每个目标独立校验 | 否则主目标校验通过会掩盖副目标写入失败，双备份形同虚设 |
| 副目标离线不阻塞主目标 | 用户可能只是忘了插移动硬盘，不应该因此让整个任务失败 |
| 计划文件一任务一文件 | 便于人工查看与清理，并与任务历史一一对应 |
| 状态每轮落盘而非每个文件落盘 | 兼顾断电后进度不丢与频繁写小文件带来的额外 I/O |
| 时间戳使用 7 位小数高精度格式 | 秒级精度会导致续传后文件时间与源文件出现亚秒级偏差（由测试用例发现） |
| 新增 UTC 专用解析方法 | 原解析方法会把带 Z 后缀的时间转成本地时间，续传后时间戳整整差一个时区（由测试用例发现） |
| 续传时不重新扫描卡片 | 计划文件已包含完整文件清单，重新扫描既慢，又可能因卡片内容变化导致计划不一致 |

## 6. 风险与回归影响

| 项目 | 评估 |
|------|------|
| 对既有流程的影响 | 未配置副目标时计划数为 1，执行路径与 v0.1.x 等价；界面新增按钮不影响旧交互 |
| 性能影响 | 多目标为线性叠加；计划文件仅在任务边界写入，单文件粒度无额外 I/O |
| 数据兼容 | 配置文件新字段缺省即表示不启用副目标；旧项目库与清单格式未变 |
| 代码重复 | 开始拷贝与继续任务两条路径有一段重复的执行管线代码（约 40 行），已记录为后续重构项；当前优先保证两条路径都稳定 |
| 未验证项 | 真机双目标写入、真机断电续传尚未实测（开发环境无读卡器与第二块盘） |

## 7. 已知限制

1. 最多支持两个目标；
2. 目标间串行写入；
3. 不自动清理异常断电遗留的临时文件；
4. 续传要求源卡与计划一致，未提供换卡继续。

## 8. 异步化与超时设计（v0.3.0 重写，修复 BUG-002）

### 8.1 v0.2.0 挂起的根因

计划生成由界面线程直接调用，且 CopyPlanBuilder 内部对每个目标做了同步文件系统访问
（Directory.Exists + 逐文件 File.Exists）。副目标为 NAS 时，数百个文件即数百次同步 SMB 往返，
界面线程被长时间占用，Windows 记录为 AppHang。

### 8.2 新的线程模型

| 阶段 | 执行线程 | 说明 |
|------|----------|------|
| 计划生成 | 后台（Task.Run） | Build 内部不再有任何文件系统访问，纯内存计算 |
| 目标探测 | 专用后台线程 + 超时 | 目录存在、可写（写探针文件）、剩余空间；默认 3 秒超时 |
| 逐文件是否跳过 | 拷贝工作线程 | 由引擎在拷贝前判断，并计入进度与结果 |
| 计划文件与历史读写 | 后台 | 续传计划、任务历史不在界面线程写盘 |
| 界面更新 | 界面线程 | 仅属性赋值与状态文本 |

### 8.3 超时实现

- 探测逻辑跑在专用后台线程（IsBackground = true），结果通过 TaskCompletionSource 回传；
- 调用方 await Task.WhenAny(结果任务, Task.Delay(超时))，超时立即返回“目标响应超时”，界面不阻塞；
- 万一探测线程被底层 I/O 卡住，它只是后台线程，不会阻止程序退出，也不会占用线程池。

### 8.4 回归测试

| 编号 | 用例 | 断言 |
|------|------|------|
| TU-BG-01 | 不可达副目标（不存在的网络路径） | 任务在限定时间内返回；主目标成功；整体为部分成功 |
| TU-BG-02 | 400 个文件 + 不可达目标 | 计划生成耗时 < 1 秒（证明已无逐文件 I/O） |
| TU-BG-03 | 目标探测超时 | CheckAsync 在超时后返回“超时”结果且不抛异常 |
| TU-BG-04 | 跳过判断已移入工作线程 | 计划阶段 Action 全部为拷贝；引擎统计跳过数量 |
