# 开发流程与评审门禁

> 本文件是项目流程的**唯一权威说明**，任何与会话记忆冲突之处以本文件为准。
> 最近更新：2026-03-10（因 F11/F12 未走评审流程而新增）

## 1. 一句话规则

**先出需求文档与技术文档 → 用户评审批准 → 再写代码。未批准不动代码。**

## 2. 标准流程（每个新功能/新需求都走一遍）

| 步骤 | 产出 | 完成判据 |
|------|------|----------|
| 1. 需求文档 | docs 下新增/更新一份需求文档：功能描述、目的、实现效果、验收标准、本期不做 | 已提交给用户 |
| 2. 技术文档 | 涉及技术、实现路径、测试用例、风险与回归影响、对现有行为的影响 | 已提交给用户 |
| 3. 评审 | 在文档中列出"待确认项"，等待用户逐条确认 | 用户回复"同意/评审通过" |
| 4. 开发 | 按批准范围实现；每完成一步提交一次；逐步运行测试 | 构建与测试通过 |
| 5. 开发说明 | 开发内容、实现方式、代码说明、测试结果、遗留问题 | 已提交给用户 |
| 6. 版本收尾 | 更新 CHANGELOG 与 AGENT.md，打 tag | 工作区干净 |

## 3. 门禁细则

1. **禁止"先做后补文档"**：即使改动很小、即使自认为方案显而易见，也必须先评审；
2. **禁止"顺手实现"**：评审期间不得修改源码，也不得在修 Bug 时捎带新功能；
3. **范围控制**：开发阶段只实现已批准的内容；发现需要变更范围时，回到步骤 1；
4. **Bug 修复的例外**：缺陷修复走"排故报告 → 审批 → 修复"，
   但若修复涉及**行为变更或功能取舍**（例如把自动格式化改成人工确认），必须按新功能流程评审；
5. **文档与代码一致**：实现与文档不一致时，以文档为基准改代码，或经评审后改文档；
6. **记录违规**：一旦发生未评审即开发，必须在 AGENT.md 的违规记录中留痕，并补交文档供评审。

## 4. 自检清单（每次准备写代码前逐条确认）

- [ ] 需求文档已产出并包含"目的 / 效果 / 验收标准"？
- [ ] 技术文档已产出并包含"实现路径 / 测试用例 / 风险"？
- [ ] 文档中列出了待用户确认的条目？
- [ ] **用户已明确回复批准？**（没有 → 停手）
- [ ] 本次改动是否超出已批准范围？（超出 → 停下来重新评审）
