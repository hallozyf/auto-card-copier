# 开发说明 · F11 多目标备份与 F12 精确断点续传（v0.3.0 重写版）

> **版本**：v0.3.0 ｜ **日期**：2026-10-12
> **背景**：v0.2.0 因 BUG-002（界面线程同步访问网络目标导致挂起）被回滚；本次按 docs/12 的 R1–R6 重写
> **评审依据**：docs/10 第 9 章补充需求、docs/11 第 8 章异步化设计（均已获批准）
> **验证**：89 个自动化用例全部通过；Debug/Release 构建 0 警告 0 错误

## 1. 与 v0.2.0 的关键差异

| 编号 | v0.2.0（已回滚） | v0.3.0（本次） |
|------|------------------|----------------|
| R1 | 计划生成、目标探测、预检都在界面线程同步执行 | 全部 await 化；探测在专用后台线程；界面线程只更新状态文本 |
| R2 | 目标检查无超时，网络不可达时无限等待 | TargetProbe 带超时（默认 3 秒），超时即判“目标不可用” |
| R3 | 计划阶段对每个文件做同步探测（网络目标数百次 SMB 往返） | 计划生成是纯内存计算；是否跳过由拷贝工作线程判断 |
| R4 | 副目标不可用时静默跳过 | 不可用目标列入结果并标记失败，汇总为“部分成功”，同时阻止解锁格式化 |
| R5 | 无目标可用性提示 | 状态显示“正在检查目标目录并生成拷贝计划…”，进度区分目标序号 |
| R6 | 无相关回归用例 | 新增 BG-01 至 BG-05 五条后台安全用例（含 BUG-002 复现场景） |

## 2. 新的线程模型

| 阶段 | 执行位置 | 说明 |
|------|----------|------|
| 目标解析（ResolveTargets） | 任意线程 | 纯字符串逻辑，不访问文件系统 |
| 目标探测（TargetProbe.CheckAsync） | 专用后台线程 + 超时 | 目录存在、可写、剩余空间 |
| 目录冲突处理（ResolveProjectDirectory） | await 之后的后台上下文 | 唯一会访问目标目录的规划步骤 |
| 计划生成（Build） | 任意线程 | 纯内存计算，400 个文件 < 20 毫秒 |
| 预检（PreflightAsync） | await 探测结果 | 空间与可写性判定 |
| 逐文件“是否跳过” | 拷贝工作线程 | 由 CopyEngine 在拷贝前判断，并计入进度与结果 |
| 计划文件与任务历史读写 | 后台 | 续传计划、历史记录不在界面线程写盘 |

## 3. 关键实现说明

1. **TargetProbe（新增）**：探测逻辑跑在 IsBackground 的专用线程上，结果通过 TaskCompletionSource 回传；
   调用方 await Task.WhenAny(结果, 超时)，超时立即返回“目标响应超时”。
   即使底层 I/O 被卡住，也只是后台线程，不占用线程池、不阻止退出、不冻结界面。
2. **CopyPlanBuilder.Build 变为纯内存计算**：不再调用 Directory.Exists / File.Exists；
   冲突处理拆分为 ResolveProjectDirectory（由协调器在后台上下文调用）。
3. **跳过判断下沉到 CopyEngine 工作线程**：计划里所有条目初始都是“拷贝”，
   引擎在真正拷贝前判断“目标已存在且一致”，计入 SkippedTargetPaths 与 SkippedFiles，并让进度条仍能到 100%。
4. **不可用目标不再静默**：v0.2.0 把离线副目标悄悄跳过，用户会误以为有双备份；
   现在它作为失败目标出现在汇总里，从而阻止解锁格式化（与 F11-E 的安全联动一致）。
5. **续传路径同步改造**：续传时把还原出的计划包成 BackupPlanSet 后走同一套协调器逻辑。

## 5. 遗留问题

| 编号 | 问题 | 说明 |
|------|------|------|
| R1 | 需用户真机验证 | 副目标设为 NAS 的 Z:\照片，拷贝 400 个以上文件：界面不卡、主副目标均写入并各自校验通过 |
| R2 | 探测线程可能被底层 I/O 长时间卡住 | 已隔离为后台线程并有超时返回，但该线程会短暂驻留；后续可评估 WNet 相关 API |
| R3 | 多目标仍为串行写入 | 若两块盘物理独立可考虑并行，需先做性能对比 |
| R4 | 跳过判断对所有目标统一在工作线程执行 | 本地目标的跳过判断由“计划阶段”后移到“执行阶段”，行为等价但时机变化；已在开发说明中记录 |

## 6. 经验

1. **“先写文档再写代码”真的能拦住这类缺陷**：技术文档早就写明“UI 线程不得做耗时 I/O”，
   如果 F11 先出文档，这条会被写进实现路径与测试用例；
2. **跨网络路径的任何调用都必须有超时**，并且不能出现在界面线程；
3. **危险相关的“静默降级”要不得**：副目标离线被静默跳过，会让用户以为有双备份——现在改为显式失败并阻止格式化；
4. **回归用例要复现真实场景**：BG-05 直接复刻了“不可达副目标 + 400 个文件”，这类用例才是防挂起的护栏。
